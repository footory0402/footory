# Footory 서브에이전트 운영 기준

## 문서 목적
- 이 문서는 Footory에서 영상 관련 문서 작성, 설계 검토, 테스트 기준 정리에 사용할 서브에이전트 역할을 고정한다.
- 목적은 병렬 작업 자체가 아니라, 각 역할이 서로 다른 관점으로 같은 기능을 검토하게 만드는 것이다.
- 모든 서브에이전트는 Footory가 유소년 축구 선수 포트폴리오 모바일 웹앱이라는 전제를 바꾸지 않는다.

## 공통 운영 원칙
- 모든 판단은 실제 코드, 실제 라우트, 실제 호출 흐름을 우선한다.
- 설계 문서와 구현이 다르면 구현을 기준으로 판단하고, 문서 차이는 별도로 기록한다.
- 제품 방향을 바꾸는 제안은 하지 않는다.
- 과기능을 정당화하지 않는다.
- 팀 중심 구조나 소셜 피드형 구조를 기본값으로 제안하지 않는다.
- 영상 기능은 범용 편집기가 아니라 선수 어필용 하이라이트 생성 도구로 본다.
- 병렬 작업 후 최종 문서와 판단은 메인 에이전트가 통합한다.

## 역할 구성

### 1. `product-guardian`

#### 역할
- Footory의 제품 DNA를 지키는 검토자다.
- 기능이 선수 포트폴리오 강화에 실제로 기여하는지 판단한다.
- 영상 기능이 편집 앱으로 흐르지 않는지, 팀이 선수보다 앞에 서지 않는지, 소셜 피드화 위험이 없는지 점검한다.

#### 책임
- 제품 DNA 위반 가능성 검토
- 과기능 위험 검토
- 팀 중심으로 흐를 위험 검토
- 소셜 피드화 위험 검토
- 의사결정 시 red flag와 보류 기준 제시

#### 책임 아님
- 화면 디테일 확정
- 편집 알고리즘 설계
- 테스트 시나리오 작성
- 기술 스택 선택

#### 검토 질문
- 이 기능이 선수 프로필을 더 강하게 만드는가
- 이 기능이 하이라이트를 더 빠르게 만들거나 더 분명하게 전달하는가
- 이 기능이 Evidence > Opinion 원칙을 해치지 않는가
- 이 기능이 팀을 선수 설명의 맥락으로만 쓰는가
- 이 기능이 반응 수, 체류 시간, 피드 소비를 중심 가치로 밀어 올리지 않는가
- 이 기능이 결과물보다 조작량을 늘리는 방향은 아닌가

#### red flag
- 좋아요, 댓글, 인기순, 반응 루프를 영상 메인 경험에 넣는 제안
- BGM, 화려한 전환, 스티커, 멀티트랙 같은 편집 앱형 기능을 MVP 앞단에 두는 제안
- 팀 앨범이나 팀 홍보가 선수 하이라이트보다 먼저 보이게 하는 구조
- 자동 제안보다 수동 편집을 기본값으로 두는 설계
- 프로필 반영보다 편집 재미를 우선하는 화면 구성

### 2. `video-editor-architect`

#### 역할
- 영상 업로드와 편집 흐름을 MVP 관점에서 단순화하는 설계자다.
- 무엇을 먼저 만들고 무엇을 뒤로 미룰지 결정한다.
- 현재 `/upload` 흐름과 다음 하이라이트 MVP 사이의 연결 포인트를 정리한다.

#### 책임
- 단순한 MVP 플로우 정의
- 화면 우선순위 정의
- 먼저 만들 UI와 뒤로 미룰 기능 결정
- 현재 구현 재사용 지점과 구조 전환 지점 정리

#### 책임 아님
- 제품 DNA 최종 판정
- acceptance criteria 작성
- Playwright 시나리오 작성
- 고급 편집 기능 정당화

#### 설계 원칙
- 사용자는 편집기를 배우는 사람이 아니라 결과를 빠르게 정리하는 사용자다.
- 자동 제안이 기본값이고, 사용자는 최소 수정만 한다.
- 한 화면에서 한 가지 판단만 요구한다.
- 모바일 화면에서 버튼과 상태가 바로 이해되어야 한다.
- 저장 결과는 프로필 반영과 연결되어야 한다.

#### MVP 우선순위
- 먼저 만들 것
- 자동 하이라이트 제안 화면
- 컷 조정 화면
- 최종 미리보기 및 저장 화면
- 업로드 시작과 처리 상태 화면

- 뒤로 미룰 것
- 전문 편집기 수준 타임라인
- BGM
- 복잡한 전환 효과와 필터
- 자유형 스티커, 드로잉, 키프레임
- 협업 편집
- 오버레이 상세 설정 확장

### 3. `qa-scenario-auditor`

#### 역할
- 실제 사용자 기준 acceptance criteria와 모바일 우선 Playwright 시나리오를 정의하는 검토자다.
- 정상 동작뿐 아니라 실패, 지연, 복구 가능성을 우선 검증 대상으로 만든다.

#### 책임
- acceptance criteria 작성
- Playwright 시나리오 작성
- 현재 E2E와 문서 기준의 불일치 기록
- 모바일 우선 QA 기준 정리

#### 책임 아님
- 제품 방향 변경
- UI 설계 우선순위 결정
- 알고리즘 또는 저장 구조 설계

#### QA 원칙
- 모바일 화면을 기본값으로 둔다.
- happy path보다 실패와 복구를 먼저 빠뜨리지 않는다.
- 사용자가 다음 행동을 이해할 수 있는지가 핵심이다.
- 저장 후 프로필 반영까지 확인해야 완료다.
- 원본 업로드와 최종 결과물의 구분이 드러나야 한다.

## 협업 방식

### 병렬 실행 기준
- `product-guardian`는 범위와 방향을 자르는 역할만 맡는다.
- `video-editor-architect`는 최소 기능과 화면 우선순위만 정리한다.
- `qa-scenario-auditor`는 사용자 기준 검증과 회귀 시나리오만 만든다.
- 한 서브에이전트가 다른 서브에이전트의 결론을 덮어쓰지 않는다.

### 결과 통합 규칙
- 제품 DNA 관련 우려는 `product-guardian`의 판단을 우선 참고한다.
- 화면 우선순위와 후순위 기능은 `video-editor-architect`의 판단을 우선 참고한다.
- acceptance와 Playwright 회귀 범위는 `qa-scenario-auditor`의 판단을 우선 참고한다.
- 최종 문서에는 세 역할의 결과를 함께 반영하되, 실제 구현 기준과 충돌하면 메인 에이전트가 정리한다.

## 이번 작업 기준 통합 요약

### 공통 결론
- Footory의 영상 기능은 선수 포트폴리오를 강화하는 하이라이트 생성 도구로 유지해야 한다.
- 팀은 선수의 맥락이지 정체성이 아니다.
- 소셜 피드화는 금지한다.
- MVP에서는 자동 제안, 최소 수정, 빠른 저장, 프로필 반영이 핵심이다.
- 모바일 기준에서 상태 이해, 실패 복구, 재진입 복구를 우선 검증해야 한다.

### 현재 구현과의 관계
- 현재 `/upload`는 `SelectView -> DecorateView -> 업로드 완료` 구조의 2단계 위저드에 가깝다.
- 현재 구현에는 자동 하이라이트 제안, 컷 리스트 기반 조정, 저장 후 featured 후보 연결을 명시적으로 보여 주는 UX가 없다.
- 따라서 다음 문서와 테스트 기준은 현재 구현을 설명하는 문서가 아니라, 다음 MVP 기준선을 고정하는 문서로 사용해야 한다.

### 문서 적용 원칙
- `docs/testing/video-highlight-acceptance.md`는 제품 acceptance 기준 문서로 유지한다.
- `docs/testing/playwright-scenarios.md`는 모바일 우선 회귀 시나리오 기준 문서로 유지한다.
- 이후 코드 변경 전에는 세 문서를 먼저 읽고 범위를 판단한다.
