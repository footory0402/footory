# 리팩터링 규칙

> Last updated: 2026-04-09

## 목적

- 영상 핵심 흐름만 남기고 주변 실험 코드와 중복 코드를 단계적으로 줄인다.
- 정리 중에도 제품 방향과 실제 사용자 흐름이 깨지지 않도록 공통 기준을 고정한다.

## 적용 범위

- `/upload` 메인 흐름
- 업로드 상태 표시
- 기본 하이라이트 제안 검토
- 컷 시작/끝 조정
- 저장
- 프로필 featured 후보 또는 하이라이트 연결

## 작업 규칙

- 정리 전에 항상 실제 import, 라우트, 테스트 호출을 먼저 확인한다.
- 문서와 구현이 다르면 구현을 기준으로 판단하고 문서 불일치를 기록한다.
- 한 번에 넓게 지우지 않는다. 이번 단계는 파일 단위의 저위험 정리만 허용한다.
- 핵심 흐름과 직접 연결된 파일은 구조 개선보다 동작 보존을 우선한다.
- 불확실하면 삭제하지 말고 `docs/archive/2026-04-10/deletion-candidates.md`를 참고하거나 plan 문서에 후보로 남긴다.

## 삭제 규칙

- 현재 `src/`, `tests/` 기준 import가 없고 라우트 진입도 없을 때만 즉시 삭제 후보로 본다.
- 현재 spec 비범위이면서 메인 `/upload` 경험을 복잡하게 만드는 UI는 우선 정리한다.
- 실험 코드라도 테스트나 앱 셸에서 호출 흔적이 있으면 즉시 삭제하지 않는다.
- 스토어 필드나 API처럼 여러 흐름이 엮인 것은 파일 삭제보다 늦게 다룬다.

## 병합 규칙

- 같은 역할의 UI가 여러 개면 먼저 호출 위치와 데이터 차이를 표로 정리한다.
- 병합 대상은 `하나를 남기고 하나를 지우는 방식`보다 `공통 유틸 추출`을 먼저 검토한다.
- 파일 선택, 업로드 준비, 메타 입력처럼 핵심 데이터 진입점은 동작 차이를 제거한 뒤 병합한다.
- 메인 업로드 컴포넌트가 커질 경우 화면 단계별로 분리하되 저장 모델은 하나로 유지한다.

## 보류 규칙

- `/api/render/*`, `/edit/[clipId]`처럼 라우트가 살아 있는 영역은 호출 근거가 완전히 사라질 때까지 보류한다.
- 테스트가 남아 있는 유틸은 테스트 정리 계획 없이 삭제하지 않는다.
- 프로필 재생, 공개 링크 재생, 업로드 저장 경로와 연결된 메타데이터 필드는 일괄 삭제하지 않는다.

## 검증 규칙

- 코드 수정 후 `npm run lint`, `npm run typecheck`, `npm run test:run`을 반드시 실행한다.
- 영상 흐름을 건드렸다면 가능하면 `npm run test:video` 또는 관련 Playwright 시나리오를 추가로 실행한다.
- 검증 실패가 있으면 실패 원인과 영향 범위를 함께 기록한다.
